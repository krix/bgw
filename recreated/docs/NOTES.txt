GAMEPLAY FIXES (2026-11-07, real-play defects)
  1. Upward-progress slowdown. The type-1 player path had been running the
     generic collision/effect spawn every frame, and types 3/4 never
     deactivated, so effect slots leaked and break.wav replayed continuously.
     Type 1 now does no generic collision/spawn; type 3 deactivates after its
     0x3c cooldown (FUN_00454214) and type 4 after +0x18 exceeds 1. A 36-frame
     standing contact now yields exactly 4 chunks and 4 break.wav requests; a
     20 s live run stayed at ~63 frames/s with at most 8 chunks / 1 popup.
     Type-2 chunks are cull-exempt (+0x28 = 1) and never deactivate, so drawFrame
     now skips entity blits fully outside the 320x240 client; GDI clips them
     anyway, so the output is unchanged (25/25 fixture frames pixel-identical).
  2. Timed-wall animation. advanceAnimatedTile now matches FUN_00452774: one
     shared +0x40 counter incremented once per frame for any solid sampled
     column, never reset by walking between columns, reset only on a
     transition; thresholds >8 / >4 / >2; leftmost column first; at most one
     transition per frame; chains 4..7, 8..11, 12..15 each end in clear; each
     transition spawns the type-2 chunk at (col*32+16, playerY+32) with
     animFrame = value-4. Native transitions land at 9-frame intervals and the
     counter survives a column change.
  3. Collectables. drawMap uses TransparentBlt with a black color key (item
     tiles now match the original capture at 0 differing pixels). Collection
     spawns the type-3 popup at the tile centre with animFrame = scoreIndex,
     awards 100/500/1000 through the 16-frame streak timer, plays get.wav, and
     the popup blinks and expires after 60 frames. Original capture shows the
     100/500 sequence and HUD 600 -> 700; native chr004 frames reproduce the
     exact 83/85/111 white/pink pixel counts.
  Evidence details are in NATIVE_STATUS.md under "Gameplay behavior fixes".

DIFFICULTY AND TIMING FIXES (2026-11-08)
  4. NORMAL/HARD played like EASY. The level remap (FUN_00456BB4) ran once at
     startup and startNewGame copied the already-remapped map, so the option
     page's GAME LEVEL never reached the map. App::initialTiles now holds the
     pristine map and startNewGame resets from it and calls
     applyLevelRemap(stateMachine.difficulty()) each run, matching the shipped
     reload (FUN_004562F4) + timed-wall remap (FUN_00456D92) per game start.
     Menu-driven capture counts (blue/green/red pixels): EASY 2625/0/72,
     NORMAL 2330/295/72, HARD 0/0/2697; EASY and HARD equal the original.
  5. Game speed / frame rate. The 16 ms busy-wait in FUN_00454535 is gated on
     SOFTWARE VSYNC (+0x32C); the shipped jne at VA 0x454CA0 skips it when the
     flag is off, so with both options off the loop free-runs at ~125 fps.
     Because physics and animation are per-frame, that ran the game at about
     double its 60 fps design; the 0x78 = 120-frame TIME unit is ~1 s only as a
     side effect of the high rate (the unpatched original ticks ~0.97 s). The
     native now locks the Win32 loop to 60 fps with a repeating 16/17/17 ms
     schedule (16.667 ms average). The TIME threshold is 60 frames (0x3B with
     the pre-increment compare) so it still advances once per second at the
     lower rate. Verified with a client-DC probe: TIME digits change every
     1.01 s (~60 frames), i.e. the logic runs at ~59.5 Hz.
     GameStateMachine::finishFrame no longer busy-waits.
  6. Settings persistence. The shipped FormDestroy (VA 0x456F7C) writes
     [button] shot/dash, [env] softvsync/waitvsync/debugflg/gamelv and
     data\rank.dat only on a graceful close. The native now writes game.ini the
     same way (in-place update, shot/dash appended after the last [button] key,
     unknown sections preserved, live gamelv) before writeRankFile. Verified
     against the original's round-trip; selecting HARD then closing writes
     gamelv=3; a forced kill leaves game.ini untouched.

RECOVERY METHOD (as actually used)
  REA's MCP provider never came up in this environment, so the analysis ran on
  the local Ghidra project and its exported decompilation instead:
    analysis\ghidra-project\BGW analyzed PE database (local, git-ignored)
    recreated\docs\decomp*.txt  exported pseudo-code per routine
    C:\mingw64\bin\objdump.exe  instruction-level checks of patched bytes
    recreated\docs\*.txt        anchors and structure notes
  Workflow: decompile a routine -> reimplement it in C++ under recreated\src ->
  build bgw.exe -> capture the original and the native with the same
  key sequence -> pixel-compare -> fix only what the evidence shows.
  Remaining work, if any, is outside rendering: audio timing and the web port.

Ghidra observations
  Ghidra selected x86:LE:32:default:borlanddelphi. The recovered central
  routine is FUN_00454535 and contains the state dispatch plus frame limiter.
  State 2 draws the LEVEL banner and advances to state 3 after 0x78 frames;
  states 2-5 share the object-update path. State 4 starts midi\miss and waits
  for completion; state 5 starts midi\gameover and invokes score insertion.
  FUN_0045552C is the menu/settings handler; FUN_004562F4 resets game state;
  FUN_00454DB8 is the scoreboard/countdown path; FUN_00456EE8 is FormKeyDown.
  FUN_00453224 is the player tile-collision path: tile 2 adds a data-driven
  score and spawns an effect; tile 3 enters state 9 and plays midi\clear.

Recent entity/map observations
  PTR_DAT_0045A498 points to the 0x34-byte entity-type table at 0x459F4C.
  FUN_00453E50 dispatches only types 1 through 4: type 1 is the player;
  types 2, 3, and 4 are falling, delayed, and animated collision/effect
  entities. No ordinary enemy update routine has been recovered.
  The type-1 table record contains 40x40 dimensions. FUN_00454535 spawns the
  player as type 1 at fixed-point coordinates (0x1000, 0x1640) = (128,178).
  The breakable score table is at 0x459F1C and contains 100, 500, 1000;
  FUN_00453224 uses these sequentially, clamping to the final value.
  The map is a 13-column by 256-row vertical shaft (see NATIVE_STATUS.md); the
  goal tile 3 sits near column 10, row 6. Native completion is triggered by
  tile collision, not by reaching an edge.
  FUN_00453B64 converts horizontal input to direction << 6 fixed-point units,
  equivalent to 2 pixels per 16 ms frame. The jump branch starts at -0x100 fixed
  units (-8 pixels/frame) and the full routine is reconstructed: gravity, the
  0xc0 (6 pixels/frame) downward cap, jump-energy scaling, and the ground-puff.
